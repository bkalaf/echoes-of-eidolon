## Required answers

### A. Existing release/version machinery

The schema already contained `Release`, `ReleaseNoteItem`, and `DeploymentRecord`; server code supported DB-backed draft creation/publication; `/api/releases` exposed published player records; `/status`, `/status/releases`, and the dynamic detail manifest state rendered basic release data; Operations included a runtime publication control; `/api/version` exposed configured build identity; exact-revision deployment and redacted records were implemented.

### B. Missing machinery

There was no canonical Markdown source, contract validator, semantic ordering, package synchronization, deterministic generated artifact, drift check, commit-footer parser, draft generator, centralized spoiler/security policy, canonical metadata, published-only sitemap expansion, or true 404 for unknown/draft release detail. Public prose could be authored separately in the DB.

### C. Valid retired concepts

The retired repository’s semantic types, filename convention, DRAFT/PUBLISHED lifecycle, conventional commit footer, player/operator audience, nonpublishing draft generator, and high-level category mapping remained useful after reconciliation.

### D. Stale retired assumptions

The retired application authority, R007/R008 ownership language, 189-screen count, `R06` Atlas claims, production Notion scope, full-game completion claims, fresh-world reseed claim, legal-draft status, and old candidate-bank detail are not current release authority.

### E. Authoritative previous release

None. No Git tag or canonical published release note proves an earlier version. No synthetic `0.1.0` history is created.

### F. Usable 0.2.0 Git boundary

The repository’s first commit through the current target is the only evidence-backed range. Historical commits predate the new footer rule, so reconstruction uses code, tests, migrations, handoff evidence, and Git history rather than rewriting those commits.

### G. Existing Status/Release Management

Both existed. Status and archive/detail screens consumed DB-published records, and administrative Release Management could create/publish those records. They were reconciled so canonical Markdown and its generated public artifact are the single source; runtime publication now fails closed.
